# 서버 검증 개선안과 보안 추가 점검 (2.2.0 검토, 2026-10-30)

이 문서는 2.2.0 코드 검토(main e694305) 7번 항목과 추가 점검 4가지를 정리한 것이에요.
바로 고칠 버그(1~6번, 정수 상한)는 PR `fix/v220-review`에서 고쳤고, 여기 적은 서버 구조 변경은 **아직 하지 않았어요**. 지섭이 정하면 단계마다 별도 PR로 나눠요.

## 1. 지금의 신뢰 경계

| 무엇 | 누가 정하나 | 서버가 막는 것 | 서버가 못 막는 것 |
| --- | --- | --- | --- |
| 게임 저장 `forest/saves/<id>` | 앱(기기) | 내 칸만 읽고 쓰기, 모양(d 글자 20만 자 안, at, v) | `d` 안의 도토리, 황금 도토리, 정수, 레벨, `u.dev`가 실제 플레이로 얻은 값인지 |
| 예전 학교 `forest/bak/<id>/0~2` | 앱 | 내 칸, 칸 3개, 모양 | 내용 |
| 랭킹 `forest/rank/<id>` | 앱 | 내 칸, 점수와 리그 점수와 시즌 점수가 10초마다 오를 수 있는 폭, 대결 점수 하루 200(2.2.0 검토 1), 메달은 대결 점수 리그까지 | 점수가 실제 저장과 맞는지, 대결 결과가 진짜인지 |
| 공개 학교 `forest/look/<id>` | 앱 | 내 칸, 4,000자, 1분 간격 | 내용 |
| 테스트 현황 `forest/stats/<id>` | 앱 | 칸 이름과 길이 | 값 |
| 광고 보상 | 앱(애드몹 SDK 콜백) | 없음 | 광고를 보지 않고 보상을 받는 조작 |

정리하면 **다른 사람의 저장을 읽거나 바꾸는 것은 규칙이 막고**, **내 기기에서 내 저장을 고치는 것은 막지 못해요**(내 계정에 임의 재화와 `u.dev=false`를 넣은 저장도 받아요). 웹판은 개발자 도구로, 안드로이드는 WebView 디버깅이나 변조 APK로 누구나 할 수 있어요. 지금 피해 범위는 그 사람의 학교와 랭킹 순위예요(남의 재화를 뺏지는 못해요).

앱 안에 공통 암호키를 넣거나 기기가 만든 서명을 붙여도 이 문제는 풀리지 않아요. 키와 서명 코드가 APK와 웹판에 같이 들어 있어서 꺼내 쓸 수 있기 때문이에요.

## 2. 대결 순위의 구조적 한계 (검토 1번)

2.2.0 검토 1번으로 대결 점수(bt)는 하루 200점(한 판 최대 +40 × 하루 5판)보다 빨리 오르지 못하게 서버 규칙(btq 시간 예산)으로 막았어요. 그래도 **한 번도 지지 않은 것처럼 하루 200점씩 올리는 것**은 막지 못해요. 서버는 경기 결과를 모르고 앱이 보낸 점수만 보기 때문이에요. 이것을 막으려면 아래 3절처럼 경기를 서버에서 판정해야 해요.

## 3. 서버 검증 개선안 (단계별)

Firebase 요금제를 Blaze(종량제)로 바꾸고 Cloud Functions(2세대)를 쓰는 안이에요. 지금 이용자 수(비공개 테스트 수십 명)에서는 무료 할당 안에 들 가능성이 커요. 콘솔에서 예산 알림(예: 월 1만 원)을 먼저 걸어 두길 권해요.

### 3-1. 1단계: 중요한 재화의 서버 장부 (황금 도토리)
- 새 경로 `forest/wallet/<id>` = `{ gold, seq, log }`. **규칙에서 앱의 쓰기를 막고**(`.write: false`) 함수만 써요(Admin SDK).
- 황금 도토리가 생기는 곳(광고 보상, 이벤트 보상, 어려운 메인 퀘스트, 업적, 랭킹 시즌)을 함수 `grantGold({ kind, ref })`로 바꿔요. 함수는 종류별 하루 상한, 같은 `ref`(예: 퀘스트 id, 이벤트 회차와 칸) 두 번 받기 막기(멱등 키 `forest/wallet/<id>/got/<ref>`), 서버 시각으로 날짜를 봐요.
- 쓰는 곳(꾸미기 백화점 등)도 함수 `spendGold({ item })`로 바꾸고, 앱은 서버 장부 값을 보여 줘요. 오프라인에서는 황금 도토리 사기를 막고 "인터넷이 이어지면 살 수 있어요"라고 알려요.
- 옛 저장 옮기기: 처음 연결할 때 저장 안의 `gold`를 한 번만 장부로 옮겨요. 상식적인 상한(예: 지금 이용자 최대값의 2배)을 넘으면 상한까지만 옮기고 운영자 확인 목록에 남겨요. 옮긴 뒤 저장 안의 `gold`는 보여 주기용 사본이에요.
- 도토리(메인 재화)는 초당 수입이 커서 서버가 따라 계산하기 어려워요. 1단계에서는 그대로 두고, 랭킹 점수 쪽(3-3)으로 막아요.

### 3-2. 2단계: 광고 보상 서버 검증
- 안드로이드(애드몹): 보상형 광고의 **서버 측 확인(SSV) 콜백**을 쓸 수 있어요. 애드몹 콘솔의 광고 단위에 콜백 주소(함수 `admobSsv`)를 넣고, 앱은 광고를 보여 줄 때 `customData`에 한 번 쓰는 토큰(함수가 미리 발급)과 사용자 id를 넣어요. 함수는 구글 공개키로 서명을 확인하고, 토큰이 처음일 때만 `grantGold({ kind: 'ad', ref: 토큰 })`을 불러요. 앱은 SDK의 보상 신호가 아니라 서버 장부가 바뀐 것을 보고 보상을 보여 줘요(몇 초 늦을 수 있어요).
- 토스: 토스 광고 SDK에 서버 확인이 있는지 콘솔 문서를 확인해야 해요(확인 필요). 없으면 토스 판은 하루 상한만 서버에서 막아요.
- 웹판(GitHub Pages)은 광고가 없어요.

### 3-3. 3단계: 랭킹 점수와 숲속 대결
- 랭킹 문서를 앱이 쓰지 않고 함수 `submitRank`가 써요. 함수는 서버에 있는 저장(`forest/saves`)에서 학교 파워를 다시 계산하고, 지난 값과 서버 시각으로 오를 수 있는 폭을 봐요(지금 규칙과 같은 폭).
- 숲속 대결은 함수 `btStart`가 상대와 난수 씨앗을 정하고, `btEnd`가 앱이 보낸 선택(종목 배치, 문제 답)을 받아 서버에서 승패를 판정해요. 그래야 2절의 한계가 풀려요. 하루 5판 상한도 함수가 서버 시각으로 세요.
- 저장 안의 재화를 고친 학교는 3-3에서도 학교 파워가 높게 나와요. 그래서 3-1 장부와 함께, 서버가 보기에 시간 대비 성장이 불가능한 학교(예: 1시간 만에 중학교)를 운영자 확인 목록에 남기는 정도로 시작해요.

### 3-4. 보조 방어: App Check(Play Integrity), 토스
- App Check는 "진짜 앱에서 온 요청인지"를 확인해 줄 뿐, 진짜 앱 안에서 값을 고치는 것은 막지 못해요. 그래서 보조 방어로만 써요.
- 적용 순서(정상 이용자가 막히지 않게):
  1. Firebase 콘솔 > App Check에 안드로이드 앱(Play Integrity)과 웹(reCAPTCHA Enterprise)을 등록하고, 앱에 App Check SDK를 넣은 판을 배포해요. **이때는 '적용(enforce)'을 켜지 않아요.**
  2. 콘솔의 App Check 지표에서 확인된 요청 비율을 1~2주 봐요. 비공개 테스트 이용자 대부분이 새 판으로 올라오고 확인 비율이 높아지면,
  3. Realtime Database와 Functions에 차례로 '적용'을 켜요. 개발용 기기와 자동 시험은 디버그 토큰을 써요.
- 시험: 디버그 토큰 없는 시험 빌드가 막히는지, 정상 플레이 스토어 설치본이 통과하는지, 사이드로드 APK가 막히는지 봐요. 토스 미니앱은 Firebase를 쓰지 않아서 해당 없어요.

### 3-5. 큰 변경을 나누는 방법
- PR A: 함수 프로젝트(`functions/`), 장부 규칙, `grantGold`와 `spendGold`, 시험(에뮬레이터). 콘솔: Blaze 전환, 예산 알림, 함수 배포(`firebase deploy --only functions,database`).
- PR B: 앱이 장부를 쓰도록(오프라인 처리, 옛 저장 옮기기), 공지 문구.
- PR C: 애드몹 SSV(콘솔에서 광고 단위 콜백 주소 등록).
- PR D: 랭킹과 대결 함수.
- PR E: App Check(관찰만) → 2주 뒤 PR F: 적용.
- 모두 운영 서버가 아니라 Firebase 에뮬레이터로 먼저 시험해요.

## 4. 추가 점검

### 4-1. 저장 검증 (숫자 기준)
- 이번 PR에서 숲의 정수(ess)는 읽을 때도 10억이 상한이 되게 맞췄어요(addEss와 같음). 정상 경제에서 정수는 하루 수백 단위라 10억에 닿지 않아요.
- 제안(아직 안 함): `sanitize()`의 숫자 읽기를 `num(v, min, max, fb)` 하나로 모아 "유한, 범위, 정수 여부"를 칸마다 표로 정해요. 도토리처럼 학교급이 오를수록 커지는 칸은 `costScale()`과 `incomeScale()`의 최대 학교급 값을 기준으로 상한을 정해야 정상 고학년 재화를 자르지 않아요(지금 s37 기준 중학교 도토리 10^16 아래).

### 4-2. 의존성 (app/package-lock.json, 2026-10-30 npm audit: 높음 6, 중간 9)
- `undici`, `@fastify/busboy`, `@grpc/grpc-js`: firebase 꾸러미의 **Node 전용** 의존성이에요. 앱은 `firebase/compat/app`과 `firebase/compat/database`만 브라우저용으로 묶어서(`app/src/fb.js`) 이 코드가 APK에 들어가지 않아요.
- `@firebase/firestore`, `functions`, `storage`: 앱에서 쓰지 않는 모듈이 감사에 걸린 거예요(번들에 안 들어가요).
- `@capacitor/cli`, `xcode`, `uuid`: 빌드 도구(iOS 프로젝트용)라 앱에 안 들어가요.
- 그래서 지금 바로 위험한 항목은 없다고 봐요. 다만 `firebase`를 10.12.2에서 최신 10.x 또는 11.x로 올리는 것을 별도 PR로 권해요. `npm audit fix --force`는 쓰지 않고, 올린 뒤 구글 로그인, 저장, 랭킹, 계정 지우기(s7, s44, s97, s98)와 광고(check_ads)를 시험해요.

### 4-3. 기기 저장과 관리자 권한
- `app/android/app/src/main/AndroidManifest.xml`이 `android:allowBackup="true"`이고 백업 제외 규칙이 없어요. 그래서 구글 드라이브 자동 백업과 기기 이전에 WebView 저장소(게임 저장, 예전 학교)와 Firebase 로그인 정보(익명 id 토큰)가 같이 옮겨질 수 있어요.
  - 장점: 새 폰에서 구글 계정을 연결하지 않아도 학교가 이어져요.
  - 위험: 같은 익명 계정이 두 기기에서 동시에 쓰여요(이번 PR의 리비전 충돌 처리로 덮이지는 않아요).
  - 제안: 그대로 두되(이용자에게 편해요), `dataExtractionRules`(안드로이드 12 이상)와 `fullBackupContent`로 Firebase 인증 저장소만 빼는 안을 검토해요. 빼면 새 폰에서는 구글 계정 연결로만 이어져요. 지섭이 정할 일이에요.
- 관리자: 지금은 `forest/adminKey`(공통 비밀 글자)를 아는 기기가 `forest/admins/<id>`에 같은 글자를 쓰면 관리자가 돼요. 글자가 새면 누구나 관리자가 돼요.
  - 제안: 공통 글자 대신 **Firebase 콘솔에서 관리자 id를 직접** `forest/admins/<id>: true`로 넣고(앱은 쓰지 못하게 `.write: false`), 규칙은 `root.child('forest/admins').child(auth.uid).val() === true`만 봐요. 더 단단하게는 Admin SDK로 커스텀 클레임(`auth.token.admin === true`)을 붙여요. 바꿀 때 지금 관리자 기기의 id를 먼저 적어 두고, 규칙 게시와 앱 업데이트를 함께 해요.

### 4-4. 코드와 그림 노출, 암호화
- 공개 GitHub 저장소, 웹판, APK에는 게임 코드 전체, 그림, 소리, `config.js`(Firebase 웹 API 키, 프로젝트 id, databaseURL), 애드몹 앱 id와 광고 단위 id, 구글 OAuth 클라이언트 id가 들어 있어요.
- 이것들은 **비밀키가 아니에요**. Firebase 웹 API 키는 프로젝트를 가리키는 이름표이고, 권한은 보안 규칙과 인증이 정해요. 광고 id와 OAuth 클라이언트 id도 앱 안에 들어가도록 만든 값이에요. 바꿀 필요가 없어요.
- 앱 안에 넣으면 안 되는 것: 서비스 계정 키(Admin SDK), 애드몹 SSV 검증에 쓰는 서버 쪽 값, 앱 서명 키와 비밀번호(keystore), 관리자 비밀 글자. 지금 저장소에서 앞의 셋은 들어 있지 않음을 확인했어요(서명 값은 GitHub Actions 비밀 값). 관리자 글자는 앱에 없고 이용자가 입력해요.
- 난독화(압축)와 파일 암호화: 코드를 읽기 어렵게 할 뿐 막지는 못해요. 복호화 키도 앱 안에 있어야 해서 꺼낼 수 있어요. 안드로이드 Keystore로 저장을 암호화하면 루팅하지 않은 다른 앱이 읽지 못하게 할 수는 있지만, 이미 안드로이드는 앱 저장소를 다른 앱과 나눠 두어서 얻는 것이 적고, 이용자 본인의 조작은 막지 못해요.
- 그래서 무리한 난독화보다 3절의 서버 검증과 규칙, 데이터 지우기를 먼저 하길 권해요. 그림 원본이 공개 저장소에 있는 것이 걱정되면 저장소를 비공개로 바꾸는 방법이 있지만, 그 경우 GitHub Pages 웹판(무료 계정)은 쓸 수 없어요.

## 5. 운영 데이터 (지우지 않았어요)
- 2.2.0 이전에 계정을 지운 이용자의 `forest/bak/<id>`, `forest/look/<id>`가 남아 있을 수 있어요. 이번 PR은 임의로 지우지 않아요.
- 정리 방법(제안): Firebase 콘솔 > Realtime Database에서 `forest/bak`, `forest/look`의 id 목록을 내보내고, `forest/saves`에도 `forest/rank`에도 없는 id(지운 계정)만 골라 지워요. 지우기 전에 JSON 내보내기로 백업해요. 원하면 이 비교를 하는 작은 스크립트를 따로 만들어 드려요(운영 서버에 쓰기 전에 목록을 먼저 보여 주는 방식).
