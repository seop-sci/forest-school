### 저장 호환과 규칙 범위

`database.rules.json`과 `dev/gh_database.rules.json`은 동일하다. 현재 저장 작성부, 백업 작성부와 옛 d/at/v 형식에 맞춰 필드를 정했다. 새 쓰기 빈도 제한은 추가하지 않았다. 부모 삭제는 Firebase의 검증 규칙 특성상 허용되고, 인증 UID 검사는 계속 적용된다. 기존 악성/허용 외 필드가 있는 문서는 부분 갱신이 거절될 수 있으므로 전체 정상 문서로 다시 쓰거나 본인이 삭제해야 한다. 운영 데이터 존재 여부는 조사하지 않았다.

at/sv는 0~253402300799999, 버전/pid는 최대32자, sum256자, why80자, r은 0~1e12 정수, d는 기존과 같은 200000자 미만이다. 백업 prog도 유한한 비음수 범위로 제한한다. 이는 데이터 크기/형태 제한이며 d 내부 재화의 진위를 서버에서 증명하는 것은 아니다.

시즌 달력 식은 기존 2026-12 시작의 분기 달력과 윤년/세기 예외를 따른다. 3000년 3월 이후에는 보수적으로 쓰기를 거부한다. 시즌 체계나 시작일을 바꾸면 규칙과 게임을 함께 수정하고 경계 시험을 갱신해야 한다.

현재 시즌 전체를 받아 정렬하므로 과거 시즌의 고득점은 조회 자리를 소모하지 않는다. 대신 참여자가 늘면 현재 시즌 전체 다운로드 비용이 커진다. 이후 서버가 관리하는 시즌별 순위 색인으로 확장하는 것이 좋다. 임의의 limit를 다시 붙이면 UID 순으로 잘려 같은 문제가 생긴다. 예전 앱의 전역 sp 조회는 예전 앱에서 계속 밀릴 수 있다. 기존 기록 경로 이동이나 데이터 삭제는 하지 않았다. Claude 공유 DB용 옛 어댑터는 대한민국 Play 출시 경로가 아니며 이번 RTDB 변경 대상으로 보지 않았다.

## 광고와 대한민국 출시

배포 국가만으로 동의 요구 여부를 추정하지 않는다. SDK가 privacyOptionsRequirementStatus=REQUIRED로 답하면 설정에 광고 개인정보 설정을 표시하고 showPrivacyOptionsForm을 사용한다. 불필요하면 숨긴다. 국가를 위조하거나 유럽용 창을 일괄 띄우지 않았다.

실제 설치 버전 @capacitor-community/admob8.2.1의 Android AdConsentExecutor.java에서 requestConsentInfo/showConsentForm의 canRequestAds/개인정보 옵션 상태 반환, showPrivacyOptionsForm 제공을 확인했다. 동의 정보 갱신 오류는 이 플러그인에서 reject만 반환하므로 로컬 캐시로 현재 SDK 판정을 대신하지 않는다. 이 경우 네트워크 복구 전까지 광고가 잠시 준비되지 않을 수 있다.

Google 공식 문서 https://developers.google.com/admob/android/privacy 는 로컬 환경에서 접근이 차단되어 최신 본문 대조는 완료하지 못했다. 실제 Android 기기에서 요구 상태, 양식 표시, 철회 뒤 재요청, 앱 재시작을 테스트 광고로 확인해야 한다. 가짜 SDK PASS만으로 실제 동의 절차를 완료했다고 보지 않는다.

## 사용자 콘솔 작업: 3.0 출시 때 순서

1. **현재는 운영 규칙을 게시하지 않는다.** PR #107을 3.0 통합 및 검수한 뒤 적용한다.
2. Firebase Console → 프로젝트 → Realtime Database → Rules에서 현재 규칙을 내려받아 보관한다. 테스트용 별도 프로젝트에 이번 database.rules.json 전체를 적용하고 익명/구글 로그인, 저장, 백업, 두 기기, 계정 삭제를 정상 요청으로 점검한다.
3. AdMob → 개인정보 보호 및 메시지에서 앱에 적용된 메시지/옵션을 확인한다. 디버그용 테스트 기기와 테스트 광고로 SDK 요구/불필요/오류/철회 상태를 검수한다. 운영 동의 상태를 위조해 광고를 요청하지 않는다.
4. 최종 서명된3.0 AAB를 만들고 AAB는 jarsigner로 서명을 확인하고 bundletool로 manifest를 확인한다. 테스트 APK를 만들었다면 apksigner와 APK Analyzer로 서명, applicationId, debuggable, 병합 manifest/권한도 확인한다. 기기 이전에서 계정과 로컬 학교가 어떻게 복원되는지 확인한다.
5. 규칙이 옛 정상 저장을 받는 것을 확인한 뒤 Firebase 운영 Rules에 이번 전체 규칙을 게시한다. 기존 sk/sp 경로를 그대로 쓰므로 데이터 이동은 없다. 게시 직후 정상 계정으로 저장/복원/랭킹 조회만 확인한다. 실패하면 원인 조사 및 보관한 규칙으로 되돌릴 준비를 한다.
6. Play Console 내부 테스트에 최종 AAB를 올려 로그인/삭제/광고/저장/랭킹을 확인한 뒤 대한민국 공개 출시한다. 개인정보처리방침과 데이터 보안 신고가 실제 Firebase/광고 수집과 맞는지도 확인한다.
7. App Check는 공급자 및 WebView 연동을 별도 구현하고 관찰 지표에서 정상 발급을 확인한 다음 단계적으로 적용한다. 지금 바로 Enforcement를 켜지 않는다. API키는 실제 API와 Android/Web 사용을 조사하고 필요한 서비스만 제한하며, Firebase/Google Cloud 예산 알림과 사용량 경보를 설정한다. 예산 알림은 비용 지출을 자동 차단하지 않는다.

## 남은 치트 위험과 우선순위

공개 출시 전 필수: 운영 규칙 일치, 실제 SDK 개인정보 옵션, 최종 서명/manifest, 저장/삭제/계정/광고 실기기 확인. 원격 시즌 조회를 쓰는 최신 버전 제공. 보상 실패 시 기본 게임 진행이 유지되는지 확인.

자기 저장의 재화/광고 횟수/test:false와 플레이 점수 위조는 서버가 실제 행동을 검증하지 않아 남아 있다. 이번 변경이 이를 해결했다고 주장하지 않는다. 클라이언트 암호화나 난독화는 사용자의 기기에서 키/코드가 필요하므로 권위 검증을 대체할 수 없다.

후속 제안: 광고 SSV에 사용자/요청 식별자와 중복 방지 장부를 연결하고 서버에서 보상 승인(중간 이상 비용, 인증/재시도/네트워크 복구 설계 필요). 경쟁 순위 점수는 서버 검증 가능한 행동으로 단계적으로 옮기기(높은 비용, 서버 운영/저장/정산/오프라인 호환 설계 필요). 시즌별 서버 순위 색인과 App Check는 부하/자동화 억제 보강이며 완전한 치트 방지가 아니다. 이번 작업에서 대규모 서버 재설계는 하지 않았다.
